# ETF Grid Maintenance Skill

This skill encapsulates the routine tasks for operating a 2% grid trading system on ETFs via Hermes Agent.

## Triggers
- User asks to clean up unconfirmed buy/sell orders after a session.
- User requests closing price collection and storage for the day.
- User wants to verify that the grid ledger is consistent with broker fills.
- User needs to generate next-day operation suggestions based on closing data.

## Authoritative reconciliation and safe rebuilds
- When the user says “只以我刚给出的数据为准，其他抛弃”, replace evidence for the named ETF only. Do not import old suggestions, inferred fills, or dates; do not reset other ETFs or the entire account.
- Display reconciliation **separately by ETF, in supplied execution order**, with stable row IDs, direction, quantity, price, and source. Include initial A-grid purchases. Suggestions are not transactions; ticket `pending` does not prove that a user never confirmed a fill elsewhere.
- Inspect explicit `partial_fills` and `filled_action` independently of whole-ticket status. “已部分成交-归档” does NOT make all its `actions` executed. Assistant-created success flags are not independent broker/user confirmation.
- Preserve unique execution IDs and explicit buy→sell references for each grid cycle. Repeated G/C rebuy cycles must not be deduplicated merely because their date, quantity and price match. Keep economic grid matching separate from physical T+1 FIFO inventory consumption.
- Unknown execution dates stay null. Sequence numbers are not dates; never advance one trading day per trade. With missing dates, report sellable quantity as unknown and block automatic executable suggestions based on that subledger.
- Before replay, inspect helper side effects: `seed()`, `load()`/migration and `apply()` may write live state. Tests and dry-runs must use isolated temporary paths or pure builders, never production seed/apply. Back up the original bytes BEFORE any mutation; restoring a backup created after damage is not recovery.
- Rebuild in memory, validate and compare, then atomically persist and read back the exact target. Do not replay every pending ticket, disable safeguards to force replay, or append historical fills to an existing balance (double-counting).
- TDD requires a real RED→GREEN cycle against production behavior. Do not implement arithmetic inside a test and call that a tested production path. Test imports must not seed live ledgers. Cover repeated cycles, idempotent replacement, fee allocation, date uncertainty and scope isolation.
- Report net invested (buy including fees minus sell net proceeds), its per-share value, and completed grid net profits separately. Remaining economic-grid purchase cost is not physical FIFO inventory cost. A standalone subledger is NOT proof that live ledger/automatic suggestions are integrated; account cash remains unverified if other ETFs are unreconciled.
- See `references/authoritative-trade-rebuild.md` for a verified nine-trade numerical fixture and acceptance boundaries.

## Stateful grid labels and cycle identity
- Grid labels are **derived state, not manually supplied trade inputs**. Under the user's current A–Z stack rule, maintain each ETF's current maximum sequence separately: no open grid = null; buy assigns successor(max), then advances max; sell assigns current max, closes that economic grid cycle, then decrements max. Replaying a complete authoritative history starts from null; incremental fills read the stored per-ETF state.
- Persist the generated label in each trade record (`lot`/grid field) along with unique execution ID; persist current maximum in the ETF summary. Never derive current maximum from the highest letter ever seen in historical/zero-quantity lots: a completed E sale must move E→D.
- Rebuying C after selling C is a new C cycle, not a new D or a manually named surrogate. Store explicit buy execution ID→sell execution ID links; grid letter alone cannot identify a cycle. Reject unmatched sells, Z overflow and unsupported partial-grid closes rather than guessing a pairing or decrementing prematurely.
- These labels track **economic grid cycles**, not physical inventory lots. Selling the current grid still requires enough pooled settled T+1 inventory; do not replace pooled settlement rules with target-grid settlement rules.
- When asked whether all data came from a script, distinguish user-supplied inputs, manually configured parameters, automatically derived fields and actually persisted output. “Present in script output” does not mean “automatically derived.” Do not claim label automation if labels were hardcoded in the input.
- See `references/stateful-grid-labels.md` for the regression fixture and integration acceptance checklist.

## Persisted holdings list (single enumeration source)
- **Every entrypoint enumerates ETFs from a persisted holdings list, never from a hardcoded tuple.** A hardcoded `CODES` tuple silently drops any held ETF from the 00:01 rollover, quote fetch, planner and monitor — an ETF in migration-exit mode then appears with `sellable_qty = null` forever, which the user will correctly call a bug.
- `holdings.py` (module) + `cache/grid-account/holdings.json` (persisted). Each entry: `code`, `name`, `lot_budget`, `active`. Deployed via `tools/confirmed_grid/deploy.py`, which writes the file and verifies every held ETF's state hash unchanged.
- **`active = false` means read-only, not absent.** The ETF is still midnight-rolled (so `sellable_qty` becomes `qty`), still listed in every report, still validated on every load; it just never receives a sell or rebuy action. This is exactly what a migration-exit ETF needs: visible, reconciled, but not traded.
- Do **not** infer or zero a missing ETF's balance. If a held ETF has no confirmed subledger, leave it out of the enumeration rather than fabricating `qty = 0`.
- Adding a new ETF is an explicit `save_holdings` call, never automatic discovery from the filesystem.
- **Enumeration is an acceptance invariant, not a completion claim.** Compare the code sets used for state loading, snapshots, daily-bar fetching, report assembly and midnight rollover. Include a third held, inactive ETF in temporary integration fixtures; two-ETF tests cannot catch a leftover two-code loop. Inactive status suppresses actions, not required valuation inputs.
- For EOD failures, inspect the exact scheduled output and compare required versus fetched keys before blaming the network. A caught `KeyError` printed as “行情或状态未验证” is a failed report, not successful risk validation. Keep state unchanged and distinguish diagnosis, implemented fix, temporary-entrypoint proof and actual scheduler proof.
- Freeze the clock in time-gated EOD regression tests at a fixed trading date after close; mocking phase alone does not bypass independent hour/minute gates. Exercise fetch plus assembly and saved-report equality, not only pre-filled report dictionaries.
- After a user requests repair and rerun, invoke the deployed entrypoint, read back the exact dated report, and compare all confirmed ledger hashes before/after. Distinguish report generation from scheduler delivery, efficiency research and rebasing; a saved report may explicitly defer the latter.
- Delayed implementation/review notifications are not new work orders: compare against the final verified version, incorporate only genuinely outstanding findings, and do not rerun fills or resurrect completed tasks. Test counts must identify their suite scope, not imply a smaller review suite contradicts a later broader run.
- See `references/eod-enumeration-acceptance.md` for the verified diagnostic, completed repair and rerun acceptance boundaries.

## Persisted inventory and midnight scheduling
- `sellable_qty` is a user-required **persisted mutable state variable**, alongside `qty` and `max_grid`; it is not a report-time interpretation. Read it from the stored ETF state when validating a sell. Script changes must save it atomically and survive process restart.
- The 00:01 rollover iterates **every code in the holdings list**, active or not. It recomputes holdings from authoritative transaction records and writes `sellable_qty = qty`. Intraday confirmed buys increase `qty` only; sells first validate the saved sellable pool, then reduce both values. Do not reset sellable inventory every time a script starts.
- Unknown original execution dates must remain unknown, but do not use that uncertainty to refuse the explicitly requested midnight state transition. Keep the date evidence separate from the user's inventory-state rule. Broker availability and frozen orders remain a separate execution check.
- Make midnight rollover idempotent by storing its update date: a repeated invocation on the same date must not restore inventory already sold intraday. Validate duplicate execution IDs and negative inventory before writing. Test disk readback, same-day repeat after a sale, buy/sell transitions, insufficient-inventory rejection without mutation, and unchanged grid pointer.
- Use the Superpowers-derived TDD skill for implementation: observe missing-behavior RED, implement, then GREEN. Test production functions using temporary state files, never invented production fills. Preserve other ETFs and unrelated fields.
- A function is not a deployed schedule. List existing cron jobs, create/update one pure-script daily `1 0 * * *` task, then read back enabled state, exact script, timezone/next run, and target file. Distinguish temporary-file execution tests, actual scheduled-script execution, and first overnight scheduler execution; do not claim one proves the others.
- A working standalone subledger does not satisfy integration into the existing fill-confirmation/09:20 suggestion path. Report the exact state files and ETF coverage; never imply all ETFs are covered when only the reconciled one is registered. Incremental confirmed fills must use the same state update path that midnight maintenance targets.
- See `references/persisted-inventory-rollover.md` for session evidence and deployment acceptance boundaries.

## Historical continuation, initialization, and runtime safety
- “继续入库” means append the newly supplied fills to the exact persisted authoritative history, not replace the earlier batch or import legacy tickets. Validate expected history IDs/count before mutation, preserve original bytes, assign new unique IDs, replay in memory, and verify the old prefix is unchanged. Do not rerun an initial fixture importer after appending: it can discard subsequent trades.
- Historical continuation with unknown dates is distinct from an intraday fill. If sellable inventory is already initialized, do not replay into a fresh state that silently resets `sellable_qty` or its update date. Use the validated incremental transition when dates are known; otherwise resolve the inventory transition explicitly without inventing dates.
- An explicit request to initialize both ETFs authorizes setting each saved `sellable_qty` to its recomputed `qty`. Back up both targets, validate both before writing, persist and read back the exact values, and retain trades, cycle links, costs and grid pointers. Report this as actual initialization, not a temporary test or inferred broker inventory.
- Before exercising a scheduled trading entrypoint, inspect whether `load()`, `plan()` or helpers can mutate state. Reproduce using isolated state or protected backups; a direct script invocation is not automatically read-only.
- If a legacy planner reads a different ledger from the authoritative subledgers, refuse stale executable suggestions and stale-ticket touch monitoring rather than filling missing positions with zero or reconstructing them from old tickets. A tested fail-closed guard is a safety mitigation, **not restored integration**. Keep the opening warning explicit and repeated minute checks quiet; retain verified subledger maintenance.
- Completion of integration requires the fill-confirmation path, midnight updater, opening planner and intraday monitor to read/write the same authoritative state, with funds, pooled inventory and outstanding orders validated. Exit code zero, standalone arithmetic tests, and the existence of a guard do not establish this.

## Fill-confirmation reply discipline (2026-10-22..26 patterns)
- **Same-price repeat confirmations are ambiguous — read the ledger BEFORE booking.** A fill message matching an already-booked trade's exact code/side/qty/price (e.g. F买 10,000@0.797 arriving again after 020 was booked at that price) may be a gateway replay of the persisted message (provider outages get retried after recovery) OR a new round of the same grid level. If a sell of that grid has since occurred, it is a new round → book fresh; if the same cycle is still open, treat as replay and skip; if genuinely ambiguous, ask the user before booking. Never book blind because the message looks valid.
- **Cross-surface reply etiquette (user pattern 2026-10-22..26):** a fill confirmation arriving on Feishu while the user is ALSO working on Desktop means the booking is handled on whichever surface received it — always finish with the ledger cross-check + refreshed `plan()` suggestions on that surface. Don't ask the user to repeat the fill on the other surface, and warn against re-sending a fill as a “connectivity test” (duplicate booking risk); suggest a plain greeting as the test message instead.
- **Booking-date caveat:** a fill reported late (message-id labeled 2026-10-24 but processed 2026-10-26) books on the LOCAL RECEIPT date. If that lands on the NEXT trading day, the T-pairing and “today N rounds” style daily stats must reflect actual booking dates read back from the subledger, not conversation-day assumptions.
- **Every booking reply must include, from real script output:** the booked trade's id/date/amount/fee read back from the subledger; a `grid_summary.summarize_account` cross-check (`cashflow_matches_ledger`) for that ETF; the paired T record when a sell closes a round (lot, buy_id→sell_id, gross, fees, net); and the refreshed `plan()` suggestions (user rule: never report holdings/pnl only). T+0 lots bought today must be explicitly called out as not adding to today's sellable pool.
- **When the user's fill is a plain attribution (“H格成交了”/“G格成立”), read the ledger to disambiguate before booking.** A bare grid-letter confirmation after several same-day fills means “the currently-advised action for that letter” — read `plan()` output + last booked trade, book the advised side/qty/price for that letter, and state the exact tuple you booked in the reply. Never ask the user to re-type details the ledger already implies; never book a guessed tuple silently either.

## Intraday alert validity window (2026-10-26 user rule, verified live)
- **A grid suggestion is only validated by touches that happen AFTER it is born** — birth = the confirmed fill that made `plan()` regenerate it. User's rule: “我说成交之后，价格涨跌到触价才有效”.
- Root cause of the false alert: old `monitor()` compared the FULL-day high/low against trigger prices. At 10:38 a buy fill (F@0.797) spawned a fresh “卖F@0.809” advice; the 0.821 morning high from the earlier E-grid session predated that advice, so the minute cron falsely alerted at 10:39 although price never revisited 0.809 after the fill.
- Implementation contract in `monitor(ticket, quotes, state, day)`: record a **baseline** (current day high/low) at each advice's FIRST SIGHTING. A valid touch is ONLY (1) current price at/through the trigger (happens now ⇒ necessarily post-birth), or (2) a NEW extreme beyond the baseline that reaches the trigger. Pregeneration extremes never validate. Alert evidence strings must read “建议生成后日内最高/最低=…（基准…）”.
- Advice disappearance (fill booked ⇒ plan no longer emits it) clears its window AND alert record, so a **reborn same-price advice re-alerts legitimately** (sell E@0.821 → fill → rebuy E → new sell E@0.821). The old day+price dedup swallowed these; state now carries `alerts` (keyed day:code:side:price) AND `baselines` (keyed code:side:price), both garbage-collected against the alive action set each run.
- Regression: `test_intraday_validity.py` — 5 RED tests reproducing the incident (morning extreme doesn't validate; new extreme beyond baseline does; first-sighting current-price touch does; reborn advice re-alerts; buy-side new low valid). The legacy `test_confirmed_runtime.py` monitor assertions were updated to the NEW semantics — when a user rule changes, rewrite tests that asserted the old behavior; don't keep both. Commit `5724005`, suite 38 passed.
- Deployment: the minute cron (`ef9a27327990`) launcher thin-imports `confirmed_runtime` from the repo, so the fix is live the next minute; no copy step. See `references/intraday-touch-validity.md` for the incident timeline and state-shape notes.

## Pitfalls
- **Do not run cleanup before the session closes** – the function assumes the market is closed and will not interfere with live orders.
- **Current state writes** use only validated `grid_state.record/rollover`; never edit confirmed JSON directly and never invoke retired `grid_account.py`.
- **Zero‑quantity rebuy entries** are harmless but accumulate; the cleanup function removes them to keep the book lean.
- **Historical unconfirmed buy orders** are only an internal reservation; the actual broker fill remains authoritative if later reported.
- **Migration guard can crash the intraday cron job** – `grid_migration.py:load_policy()` raises `ValueError` when `migration.json` has `target_buy_enabled: true` without manual broker verification. This propagates through `grid_weixin_intraday.py:trend_alert()` → `guard_ticket()` → `load_policy()` and kills the `ef9a27327990` (盘中检查) cron job. See `references/migration-guard.md` for the full error surface and recovery steps.
- **Volume unit mismatch in `grid_model.py` (FIXED 2026-10-14, corrected after independent review)** – three volume checks (lines 37, 76, 88) compared share-denominated quantities (`core_qty+4*q`, `qty`) against lot-denominated `vol[i]*.01`. Sina K-line `volume` is in lots (1 lot = 100 shares); the model internally uses shares. The 100x mismatch silently rejects any ETF whose first-bar volume is below ~2.3M shares — 159569 (1.46M lots) was wrongly blocked while 589720/159363 (70M+ lots) passed trivially. Fix: multiply `vol[i]*.01` by 100 in all three places so the 1% threshold is share-denominated. **The first fix applied `*100` to lines 37 and 76 but missed line 88 (the buy-side check); an independent reviewer caught it because the original tests did not exercise line 88.** When fixing a unit mismatch, verify every occurrence of the comparison, not just the ones that reproduce the reported symptom. See `references/grid-model-volume-unit-fix.md` for the verification recipe and why the original tests were not sufficient.
- **`cycle_return_on_40k_pct` denominator was hardcoded to 40,000 (FIXED 2026-10-14)** – line 125 used `cycle_pnl/40000*100` as the denominator. The actual trading-lot capital is `4*c` (4 × `purchase(5000, initial_p)` cost, ≈20,000 CNY), not 40,000. This understated the return-on-capital metric by ~2x. Fixed to `cycle_pnl/(4*c)*100 if c else 0.0`. When a metric name contains a hardcoded number, verify the denominator matches the actual capital at risk.
- **Initial invariant assertions were missing (FIXED 2026-10-14)** – lines 59-67 now check `cash >= 50000` and `cost_held <= 50000` immediately after initial position setup, rather than waiting for the first bar's loop assertion (line 110). Catches parameter regressions earlier. When adding assertions, place them at the earliest point where the invariant can be violated, not at the first loop iteration.
- **T+1 settlement logic in `grid_model.py` is correct** – the `available` pool resets to `qty_total` at each new trading day (line 70), but new buys do NOT add to `available` when `t0=False` (line 102). This means today's buys cannot be sold today — genuine T+1. Earlier criticism of this pattern was incorrect; the reset is for overnight settlement, not a bug. When reviewing settlement logic, trace the full buy→available→sell path across day boundaries before calling it a bug.
- **Hardcoded values must be traced through BOTH files (FIXED 2026-10-15)** – `grid_model.py` had `purchase(5000, p)` hardcoded on the buy-side loop (line 100) even after other fixes, and `engine.py` line 126 had `gap=.02` hardcoded in the caller. When parameterizing a model, check: (a) the callee's signature and all internal call sites, (b) the caller's invocation site, (c) any other callers that bypass the new parameter. A value that appears in two files needs both touched. Default values must preserve backward compatibility (e.g. `lot_budget=5000`, `gap=0.02`) so existing callers don't break. See `references/grid-model-parameterization.md`.
- **The patch tool can corrupt Python indentation** – when replacing multi-line blocks, the tool may introduce 8-space indent where 4-space is needed. Binary-level replacement (`open(path,'rb').read().replace(old_bytes, new_bytes)`) is more reliable for precise edits. After any patch, run `python -c "compile(open(path).read(), path, 'exec')"` to catch syntax errors before running tests.
- **Box bounds must be verified against actual price range** – `etf-grid-screener` reports bounds from an 80-day window. Always cross-check against the actual 63-day price range before trusting grid levels. A reported upper bound may never have been touched; a reported lower bound may have been breached. Example: 159569 screener box 1.378–1.480 vs actual range 1.280–1.445 (73.4% of days inside box).
- **Cost basis model (2026-10-09 user-corrected)** – `pos["cost_cash"]` must equal **net invested = total buy costs (含费) − total sell proceeds (含费)**, NOT the sum of remaining lot buy costs. A sell does **not** reduce the cost basis of remaining shares; the user tracks total money put in minus total money taken out. The old `apply()` logic subtracted `take × source["price"]` from `cost_cash`, which understated the basis and produced a phantom "浮盈". The correct sell path in `apply()` is: `pos["cost_cash"] = round(pos["cost_cash"] - proceeds, 2)` where `proceeds = notional - commission`. Rebuild cost_cash from `history` by summing per-code buy costs and subtracting per-code sell proceeds; never derive it from lot-level arithmetic after a pooled T+1 sell.
- **Research ranking numbers are not comparable across models or windows** – the codebase has two simulation engines with different constraints. `grid_model.py` (5-minute bars, 100k account, 1元 minimum commission, 0.05% slippage, T+1 settlement, 1% volume cap) produces far fewer round trips than `simulate_daily_grid` (daily close proxy, no fees, no slippage, no inventory constraints). A 104-day window produces more round trips than a 63-day window for the same ETF. **Before presenting any ranking table, state the provenance header explicitly: engine name, window start→end, session count, fee assumptions, and whether offline cache or live quotes were used.** Explicitly name which prior numbers are NOT comparable and why. The user will otherwise reconcile the new table against a different model/window they remember, and correctly call it a wrong push. A table without a provenance header is a presentation failure, not a minor omission.
- **`rotation_top10` was derived from an already-filtered `rotation` list (FIXED 2026-10-16)** – `engine.py` computed `rotation` as `rank[has_all_four_windows & ~holding & full_cycles > baseline]`, then set `rotation_top10 = rotation.head(10)`. Since `rotation` already filtered to only candidates beating the baseline, `rotation_top10` returned at most 2 items instead of the full top 10. Fix: derive `rotation_top10` directly from the full ranked list (`rank[has_all_four_windows & ~holding].sort_values(...).head(10)`), keeping `rotation` separate for leader detection. **When a derived output is computed from an already-filtered intermediate, the filter silently propagates. Always trace the full derivation chain before trusting a ranked list.**
- **Pooled T+1 sell does NOT consume the target lot** – when a sell hits a grid price (e.g. C格) whose lot was bought same-day (T+0), the shares are drawn from the pooled T+1 inventory (oldest settled lots first, FIFO), **not** from the target lot. The target lot's `qty` stays untouched. The old code zeroed the target lot's qty, which desynced `pos["qty"]` from the sum of lot qtys. Always call `sync_qty(pos)` after a sell so `pos["qty"] == sum(lot["qty"])`.
- **When reconciling with the user, compute cost basis from history, not from lot state** – the user will independently sum `buy costs − sell proceeds` and compare against `cost_cash`. If the numbers differ, the discrepancy is almost always in the sell-side cost reduction path, not in the buy records. Walk through each trade one at a time; the user will correct you down to the yuan.
- **复盘"少赚了T"类反事实必须先拉分钟数据审计（2026-10-28）** – 先查当前北京时间确认用户说的"今天"是哪个交易日（跨日会话里极易错位，本次差点按前一天复盘）；再区分网格口径的T（买卖均在网格点闭环）与波段口径的T（如 0.756买→0.772卖）。网格口径下 G买@0.785 即使成交，G卖@0.797 当日未触及即闭环不成立——"没吃到的T"可能根本不在网格目标市场里。卖单差几厘未触发是网格点运气，不是门控的锅（门控从不拦卖出）。结论必须回到规则层面：单日结果不评判规则——按规则放弃的盈利和违规躲过的亏损长期是一回事。
